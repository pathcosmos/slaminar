# Performance Baseline — slaminar v0.9.4

> 측정일: 2026-04-20 · 기준 빌드: v0.9.3 (pre-release) · 환경: macOS (darwin arm64), Node.js 22.20.0

## 측정 방법

두 레이어의 벤치마크:
1. **CLI wall-time** — `scripts/bench-cli.mjs`. `node dist/cli.js init --dry-run` 을 spawnSync 로 띄우고 process 수명 전체를 `performance.now()` 로 측정. Node 시작 비용 포함.
2. **Library phase breakdown** — `scripts/bench-lib.mjs`. `dist/core/scanner.js`, `dist/core/pipeline.js`, `dist/recommender/recommender.js` 를 직접 import 해서 `scan()` / `analyze()` / `recommend()` 를 in-process 로 호출. Node 시작 비용 제외.

**Warmup**: 각 시나리오 앞에 2–3 회 미계측 실행으로 FS 캐시 워밍.
**Runs**: CLI bench n=8, lib bench scan/analyze n=15, recommend n=10. Mean / stddev / min / max.
**AI**: `SLAMINAR_AI_PROVIDER=local` 으로 외부 호출 0 (결정적).
**Version check**: `SLAMINAR_VERSION_CHECK=false` 로 네트워크 없음.

**관찰**:
- **Fixture 크기에 대한 선형 증가 약함**: 20 → 5000 파일 (250×) 에 wall-time 102ms → 124ms (22% 증가). 대부분이 상수 startup.
- **Tier 는 wall-time 에 사실상 영향 없음** (< 2ms). token-cost tier 는 post-recommend 필터링이라 I/O 비용 대비 무시 가능.

## 2. Library-level phase breakdown

| Fixture | Phase | mean | stddev | comments |
|---|---|---|---|---|
| small | scan | 287µs | ±46µs | 파일 트리 + git log + package.json read |
| small | analyze | 271µs | ±32µs | scan + 5 analyzers (거의 무비용) |
| small | recommend | 685µs | ±287µs | 첫 호출 catalog load 포함 |
| medium | scan | **2.1ms** | ±257µs | 500 files |
| medium | analyze | 2.2ms | ±154µs | 5 analyzers ≈ 0.1ms |
| medium | recommend | 197µs | ±56µs | warm cache |
| large | scan | **13.6ms** | ±492µs | 5000 files |
| large | analyze | 13.5ms | ±1.1ms | 5 analyzers ≈ 0ms 측정 오차 |
| large | recommend | 176µs | ±82µs | warm cache |

**관찰**:
- **파일 트리 walk 비용이 linear (~3µs/file)** — large 에서 scan 13.6ms / 5000 파일 = 2.7µs/file.
- **Analyzer 5 개의 비용은 사실상 0** — analyze 와 scan 의 차이가 측정 오차 수준.
- **recommend 는 첫 호출 warmup 비용** (+500µs) 후 ~200µs 로 수렴. Catalog cache 가 잘 작동.

## 3. Top 3 병목 (개선 여지)

### 병목 #1 — Node.js 시작 + 모듈 로드 (~90ms = CLI wall-time 의 ~80%)

CLI 의 총 wall-time 100–130ms 중 library pipeline 은 <20ms 이고 **나머지 80–110ms 는 Node 시작 + require 체인 + commander parse**.

**정량화**: Large fixture 에서 library pipeline 대략 14ms, subprocess wall-time 124ms → startup 오버헤드 약 110ms.

**개선 후보** (모두 large 범위 변경):
- **Single-file bundle (esbuild)** — require 체인 대신 single CJS/ESM 번들. 기대: 20–40ms 절감.
- **Native 바이너리 (pkg / nexe / bun compile)** — startup 한 자리수 ms 가능, 배포 사이즈 증가.
- **Node cache 디렉토리 재사용** (`--node-options=--experimental-compile-cache`). 세션 내 반복 호출에 효과.

**결론**: 현재 사용자 체감 wall-time 은 스크립트 호출 기준 ~100ms — 쾌적 범위. 적극 개선은 P2 로 유지, 수치만 baseline 에 고정.

### 병목 #2 — `scan` 의 파일 트리 walk (선형 N × 3µs)

대형 monorepo 에서는 지배적. Large fixture 에서 13.6ms, 이론상 50000 파일 프로젝트면 ~136ms (pipeline 만).

**개선 후보**:
- `fs.readdir` 를 `recursive: true` + `withFileTypes: true` 로 한 번에 읽기 (Node 20+). 현재는 재귀 루프.
- `fs.promises.readdir` 로 병렬화 (worker thread 없이도 I/O overlap).
- `scanner.excludePatterns` 가 이미 `node_modules/.git/.venv/...` 를 제외하므로 실제 훑는 파일 수는 제한적. fixture 가 `.gitignore` 스타일을 더 공격적으로 적용하면 scan 비용 감소.

**결론**: P2 — 대부분 사용자는 medium 이하 프로젝트. 10K+ 파일 프로젝트 요청이 생기면 그때 착수.

### 병목 #3 — `recommend` 첫 호출의 catalog 로드 (~500µs 1회)

함수 호출 자체는 작지만, `recommend()` 가 cold 로 호출될 때마다 bundled catalog JSON (catalog/catalog.json, 56 tools) 을 `readFile + JSON.parse` 함. CLI 실행마다 한 번 — single-file invocation 에서는 무의미하지만 init + recommend 를 연속 호출하는 배치 경로 (discover batch apply) 에서는 누적.

**정량화**: 현재 batch apply 는 각 프로젝트마다 새 CLI 프로세스를 띄우므로 이미 프로세스 경계에서 격리됨. 실질 영향 0.

**개선 후보**:
- In-process memoize (module-level cache): `const cached = await loadCatalog(); return cached;`
- discover batch apply 를 subprocess-per-project 대신 in-process 로 전환 시 catalog 1회 로드.

**결론**: P2 — 현재 CLI 모델에선 매 invocation 이 cold start 이라 memoize 효과 0. batch apply 리팩토링 시 같이.

## 4. Regression 방지 계약

- v0.9.4 baseline 은 위 수치. 후속 릴리스에서 `npm run bench` 결과가 **±10% 이내** 유지되어야 함.
- 10% 이상 regression 시:
  - CI 에서 이 파일과 새 raw/ 결과를 diff 하여 flag (자동화는 향후)
  - 수동: `docs/benchmarks/raw/` 의 새 .json 과 기존 baseline 숫자 비교
- baseline 갱신은 의도된 architecture 변경 후에만 (새 raw 타임스탬프로 갱신 commit).

## 5. 주의사항

- 측정 환경 의존: 수치는 macOS M-series 로컬 기준. GitHub Actions runner (Linux x86_64) 에서는 절대값이 다를 수 있으나 **상대 비율**은 유지되어야 함.
- Stddev 가 mean 의 20%+ 인 케이스 (small recommend, large analyze) 는 첫 호출 노이즈 또는 FS 캐시 변동 — 해석 시 유의.
- `npm run bench:cli` 는 ~3분, `bench:lib` 는 ~2초. CI 에서는 `bench:lib` 만 게이트로 둘 것을 권장.
